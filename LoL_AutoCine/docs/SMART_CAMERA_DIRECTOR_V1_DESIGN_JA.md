# Smart Camera Director v1.0 — 受領仕様と実装前の設計案

2026-10-18。ユーザーがこの日のチャットで提示した仕様を正式な入力とする。GitHubの旧資料にある良好／不良カメラ番号より、本書の保護条件を優先する。本書は設計案であり、新モードの実装・実機合格を示すものではない。

## 確定した要求

- 基本モードを「従来の手動」「固定視点＋自動構図補正」「フルオートシネマ」の3つにする。置き換えず追加する。
- 手動では通常3人称、3人称シネマ、FPS風、Orbit、Lolnam、俯瞰、TargetLock、手動調整、既存テンプレート／プロジェクトを維持し、自動制御を無効にできる。
- 固定視点補正では選択したカメラ種類を維持する。距離・高さ・追従角度・FOV・画面内位置・キル前後の動きを滑らかに調整し、反転・急変・画面外れを防ぐ。座標が不成立なら安全な既存構図へ戻す。
- フルオートではPRE／KILL／POSTの見やすさを優先し、複数キルは広い構図を選べる。QA合格視点を優先し、不安定視点を除外できる。同じ入力と設定で同じ選択となり、切替は安全なショット境界で行う。選択不能なら固定視点へ戻す。
- BLUE/REDを独立管理。重点調査はBLUE6/9/10、RED1/3。保護対象はRED2/4/5と良好な3人称斜め後ろ。今回これらの角度を推測変更しない。
- 白基調UI、初心者ワンクリックを維持。詳細な自動化強度は詳細編集側に置く。
- 144Hz相当の内部計算と実際のAPI送信頻度・遅延を分け、時刻補間、録画／音声同期、1920×1080/60fps、GPU/NVENC、LoL専用音声を維持する。
- 敵の3D位置・地形遮蔽・戦闘動作を取得できない場合は、推定を取得済みの事実として記録しない。判断とフォールバック理由をログに残す。
- 数式・しきい値・優先順位は未確定。現行コードとWindows実測を踏まえ、具体的な変更を実装前に提案する。モック合格を画角の合格にしない。

## 既存実装の棚卸し

|所在|確認できた機能|仕様に対する不足|
|---|---|---|
|`core/camera.py:CameraPlan`|`smart_composition`による距離／仰角の制約、キル周辺のdolly/FOV/Orbit、keyframes、`_director_gain`|選択した3モードを区別する制御契約、観測可能性に基づく補正理由の記録|
|`core/camera.py:CameraDirector`|SmoothReplayClock、姿勢／FOV平滑化、API遅延に応じた送信、実送信offsetに整合する視線、TargetLock heartbeat|QA許可リストからのショット決定を受け取る入口。新しい送信ループは不要|
|`core/jobs.py:_setup_clip`と録画準備|チーム／スタイル別校正、対象相対pose、stale座標拒否、録画開始前の姿勢確認|モード別の決定記録を録画前に確定する結線|
|`ui/highlight_director.py`|キル数／assistからchase/impact/teamfightを決定、始終点が中立の5キーフレーム|カメラ種類をQA状態から選択する機構。敵位置認識ではない|
|`legacy_app.py`|スマート構図チェック、自動ディレクター強度、ワンクリックへのsnapshot伝達|3モードの明示選択、固定視点での種類保持、独立した自動候補設定|
|`core/effects.py:Template`、`ui/scene_project.py`|既存保存と省略可能な追加フィールド、scene単位の設定|新モードの保存／再読込／旧データの無変更経路|

現行`smart_composition`には例えば最低仰角や距離係数の既存定数があるが、実機未確認の新しい最適値へ変更しない。値が存在することは空・地面・遮蔽を実画像で検知できる証拠ではない。

## 提案する小さな構成

1. Template末尾に省略可能な制御モードを追加する。明示値は`manual`／`fixed_auto`／`full_auto`の3つとする。フィールドがない旧データは内部の互換経路で読み、既存`smart_composition`／`auto_director_strength`の意味と手動値を保持する。これは4つ目の基本UIモードを追加する案ではない。ユーザーが明示的に手動を選ぶと、新しい自動補正と自動選択を無効にするが、保存していた手動値や詳細設定は消去しない。旧フィールドを一括で新設定へ変換しない。
2. ショット決定は純粋関数にする。入力はイベント時刻／キル数／role、チーム、選択style、ユーザー設定、QA候補台帳。出力は既存CameraPlanへ渡す決定と理由。カメラ通信・音声・GPUをこの関数から呼ばない。
3. 固定視点ではstyleを不変にし、既存計画を基準に補正包絡を適用する。CameraDirectorを1つだけ使い、平滑化後の実際の送信poseと視線の一致を維持する。
4. フルオートの初期段階では1クリップ1種類を録画前に決める。PRE/KILL/POSTは既存の連続した包絡で変化させる。種類の切替はクリップ境界に限定し、録画中のモード再校正によるジャンプを避ける。将来の途中切替は別途安全な分割・接続の検証を行う。
5. QA台帳はBLUE/RED×style別に、承認状態、検証版／fingerprint、適用条件、除外理由を持つ。未確認を合格扱いしない。候補が空なら指定の固定視点へ戻し、理由を記録する。現時点で新仕様用の正式な合格プールは未確定。
6. 新ログには入力イベント、モード、元style、採用style、補正前後pose、API遅延、座標の有効性、決定理由、fallback理由、コード識別子を含める。個人名・録画・診断生データは公開Gitへ入れない。

## 実装前に決める事項

- 同一リプレイ・対象・イベントの最新映像から、BLUE6/9/10とRED1/3の原因と、RED2/4/5の保護基準を確定する。
- 補正量・角速度・FOVの上限は、既存制約との関係を表にして提案する。新しい数値の実測根拠はまだない。
- 自動選択の初期優先順位と固定fallbackをチーム別に提案する。過去の「RED3/5良好」を今回の自動合格台帳へ転記しない。
- 画面内の選手位置や地形遮蔽を何で観測できるかを確認する。イベント情報だけの場合はメタデータ由来の演出までとし、視覚認識による構図保証と呼ばない。

## 検証順序

環境復旧→既存回帰→旧モード出力の固定→固定視点補正→自動選択→Windows同一シーンQA→必要なモードだけ修正→配布。
90°/180°、BLUE/RED、PRE/KILL/POST、複数キル、API遅延／欠損、座標stale、無効値、候補なし、旧データ再読込、録画非開始、同期を自動検証する。最終画角・ターゲット視認・操作性・LoL音だけの収録はWindows実機で確認する。


## 2026-10-19 実装追記（数値検証済み・LoL実映像QA未確認）

前節までは10月18日の設計記録。本節の変更は復旧版 de453046 を基準にした追加であり、過去の動画を再視聴したという意味ではない。privateのBLUE/REDテスト動画は取得できていないため、BLUE6/9/10・RED1/3の最終的な原因確定とRED2/4/5の映像比較は保留する。

### 実装した契約

- Templateの`camera_control_mode=None`は旧挙動を数値維持する。`manual`では新しい自動補正を無効化し、保存済み手動値は消去しない。`fixed_auto`は選択styleを維持。`full_auto`は録画前の1クリップ1種類だけ決め、実行中にstyleを切り替えない。
- `core/smart_camera_director.py`は純粋な選択関数。入力はモード、BLUE/RED、選択style、有限なイベント時刻、明示QA承認台帳、除外リスト。敵3D座標や画面内の人物検出は行わない。
- `camera_auto_qa_approved`は`{"BLUE": ["third"], "RED": [...]}`形式。初期は空。過去の良好カメラ番号を自動転記しない。明示承認されたstyleだけ自動選択候補にする。
- `camera_auto_excluded`はstyle名で両サイド除外、`BLUE:third`/`RED:third`で片サイド除外。除外styleをfallbackにも採用しない。候補がない場合は指定styleの固定補正へ戻り、指定styleも除外されていれば安全なtopへ戻る。これは視覚品質の合格判定ではない。
- 単独イベントはthird_cinema→third→lolnam_cinema→cinema_top→follow→cinema→top→geo_aim→fps→orbit、複数イベントはcinema_top→top→third→third_cinema→follow→cinema→geo_aim→lolnam_cinema→fps→orbitの順。候補台帳に存在するものだけ採用する決定的な初期順序。実機比較後に変更可能。

### 軸・追従の安全策と旧機能保護

旧校正はtop側のEulerからpitch軸を推定するため、stale座標と別styleの回転を組み合わせると、yawをrollへ送り上下反転する経路がある。v5.10.27ですでに対象/モードごとのcache分離、7モードの軸修正が導入されている。本変更はこの旧修正を重複実装せず、新モードだけ同じ安全契約を全fps系/Orbitへ拡張する。

- 新モードは`safe_axes=True`で同じ対象のtop/fps基準ペアを読み、選択名・attached・mode・ZERO offset・有限座標・距離・高さが不一致なら最大2回再取得する。成立しなければ既存topへ戻る。過去の絶対Pや別styleのcacheは採用しない。
- 新モードcacheには`smart_v1`区分を付け、旧手動校正を汚染しない。旧NoneのRED FPS/geo_aimやRED2/4/5用の数値調整は変更しない。
- 位置から視線を毎回算出し、X=yaw/Y=下向きpitch/Z=0を使用。144Hz計算→offset平滑化→API遅延時の移動制限の後、**実際に送るoffset**から再度視線を算出する。これにより90/180度や角度境界で位置と向きの時刻を分離しない。
- 新モードの明示手動yawは0/90/180度をそのまま保持し、自動keyframe/kill補正だけ既存の±55度範囲に制約する。旧Noneのclamp数値は維持。
- 新モードOrbitは旧実験モードのcue外半径0を避け、既存third距離/高さを基準に相対公転する。旧手動Orbitは変更しない。
- 新モードは既存FOV範囲32〜100度とtarget_center_rotationの14〜72度に合わせて有限な相対poseを構成する。複数キルのfull_autoはFOVを既存基本60度未満にしない。無効poseは有限な相対rear offset `(0,650,-1050)`へ戻し、理由を一度ログへ記録する。これは暫定安全境界であり、見た目の最適値を実測したものではない。
- `_vec`でNaN/Infinityを拒否し、位置検証の`NaN > threshold == False`による誤合格を防ぐ。通常の有限入力結果は変わらない。
- 録画前の最終pose読み戻しを新モードに適用。新モードのプレビューも同じ確認を行う。確認失敗時は録画/音声開始前に中止する既存経路を利用する。
- フルオートでstyleが変化した場合の録画timeoutだけ既存最低シネマ速度0.35を考慮。音声/GPU/録画のクロック、SmoothReplayClock、API更新頻度、HUD復帰は維持。

### 診断と検証範囲

`SMART_CAMERA_DECISION`にモード、対象サイド、元style/採用style、イベント時刻、理由、fallbackを保存。`SMART_CAMERA_FALLBACK`に基準不成立または無効poseと`visual_qa_pass:false`を記録。既存`CAMERA_QA_BASELINE`/`CAMERA_QA_POSE`/`CAMERA_QA_INITIAL_POSE`とAPI遅延診断を引き続き使用する。個人名や診断生ログを公開Gitへ追加しない。

`tests/test_smart_camera_director_v1.py`はBLUE/RED×全10style×固定/フルオート×0/90/180度、同一選択2回、送信時の追従向き、低速API、欠損/stale/non-finite、明示manual、台帳とサイド別除外、決定再現性、複数キル優先順位、Template実保存/再読込を検査する。これらは数値・制御契約の検証。人物の可視性、地形遮蔽、FPSらしさ、RED2/4/5の実映像回帰、上下反転の見た目はWindowsの同一リプレイ比較で別途判定する。

サイド設定をblue/redへ明示固定した場合は、実際に使用する補正側のQA台帳で候補を選ぶ。フォールバックでも除外済み視点を再採用せず、全視点が除外されていれば理由を記録し録画前に中止する。
