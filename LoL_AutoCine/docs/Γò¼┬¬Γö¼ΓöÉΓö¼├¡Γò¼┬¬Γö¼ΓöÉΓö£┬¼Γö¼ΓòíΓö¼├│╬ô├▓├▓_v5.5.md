# LoL AutoCine v5.5 設計書

## 1. システム構成

```text
Tkinter UI
  ├─ 左ワークフロー
  ├─ 中央 PanedWindow
  │   ├─ LoLミラー / カメラプレビュー（固定）
  │   └─ 編集エリア ScrollFrame（可変）
  └─ 右設定 ScrollFrame
       ↓
ReplayAPI
       ↓
CameraDirector ── CameraPlan / TargetLock
       ↓
WGCWindowSource
       ↓
ClipRecorder
       ↓
FFmpeg GPU-first pipeline
       ├─ CUDA decode / scale（利用可能時）
       ├─ CPU-only filter（必要な効果のみ）
       └─ NVENC encode
       ↓
Audio Capture
       ├─ ProcessLoopbackRecorder
       └─ SessionIsolatedLoopbackAudio fallback
       ↓
Audio Mux
       ↓
1080p MP4
```

## 2. UI設計

### 2.1 3ペイン

- 左: 310px前後
- 中央: 可変幅
- 右: 390px前後
- 左右は縦スクロール。
- 中央は上下Split。

### 2.2 中央Split

`tk.PanedWindow(orient="vertical")` を使用する。

- `preview_host`: minsize 360px
- `edit_host`: minsize 250px
- 初期比率は約56%をプレビューへ割り当てる。
- `edit_host` のみ `ScrollFrame` で縦スクロールする。
- プレビューCanvasは `fill="both", expand=True` とする。

これにより、設定を大量に追加してもミラーがスクロール領域の外へ追い出されない。

## 3. スクロール設計

`ScrollFrame` は内部Canvas＋Scrollbarを持つ。

マウスホイールは画面全体にbindするが、ポインタが該当ScrollFrame内にある場合だけそのScrollFrameをスクロールする。

中央については `edit_host` のScrollFrameだけがホイール対象になるため、プレビューは固定される。

## 4. カメラ設計

### 4.1 TargetLock

対象プレイヤーを `selectionName` として固定する。

三人称では `selectionOffset` を対象中心からのカメラ位置として利用し、回転値を同じOrbit角から計算する。

### 4.2 LoLnam風Orbit

```text
kill - 2.0s
     ↓
  ease-in
     ↓
  Orbit開始
     ↓
  kill impact
     ├─ FOV変化
     ├─ ドリーイン
     └─ ローアングル
     ↓
  ease-out
     ↓
kill + 1.8s
```

すべて `smoothstep` / quintic ease を基本とし、キル瞬間の不連続な値変更を避ける。

### 4.3 ガクつき対策

従来の問題は以下が重なることで発生する。

- Replay APIがHTTPS/HTTP通信である。
- カメラループが毎回 `playback GET` を行っていた。
- さらに毎回 `render POST` を行っていた。
- キル時にはFOV、速度、Orbitが同時に変化する。
- HTTP待ちによってカメラ更新周期が不規則になる。

v5.5では以下へ変更する。

1. モーション計算は144Hz。
2. `time.perf_counter()` から再生時間を連続推定。
3. Replay APIの実時間は0.25秒間隔で同期。
4. Replay APIへのrender送信は最大60Hz。
5. FOV/offset/rotationは指数平滑化。
6. 再生速度も平滑化。
7. APIエラー時は直前の補間状態を維持。

「144Hz = HTTPを144回送信」ではない。これは負荷とガクつきを増やすため、内部補間とAPI通信を分離する。

## 5. プレビュー設計

- `_preview_tick` は短い間隔でUIを更新する。
- 目標は144Hz相当。
- WGCが実際に供給できるフレームレートを上限とする。
- フレームが到着しない場合は最後のフレームを使用する。
- 編集領域をスクロールしてもCanvasを破棄しない。

## 6. 録画設計

### 内部キャプチャ

- 144fpsを標準内部キャプチャ値とする。
- これにより60fps書き出しでも元となるカメラモーションを高頻度で取得できる。

### 最終出力

- 標準: 1920x1080 / 60fps / H.264 MP4
- オプション: 1920x1080 / 144fps
- CFRを強制する。

## 7. GPU設計

### 優先順位

1. NVIDIA CUDAデコード
2. CUDA GPUリサイズ
3. NVENC H.264エンコード
4. GPU非対応フィルタのみCPU
5. NVENC/CUDAが無い場合CPUフォールバック

FFmpegのすべてのフィルタがCUDA版を持っているわけではない。そのため「全フィルタをGPU化する」のではなく、「GPUで可能な処理を常に優先する」設計とする。

## 8. 音声設計

### 8.1 取得

`PreferredGameAudio` を使用する。

```text
PreferredGameAudio
      │
      ├─ core.audio_worker
      │      └─ ProcessLoopbackRecorder
      │
      └─ 失敗
             ↓
      SessionIsolatedLoopbackAudio
             └─ LoL以外を一時ミュート
```

### 8.2 なぜミラーでは音が入り、出力で消えるのか

ミラー表示はWindows上のLoL出力をそのまま聞いているため、音声処理を必要としない。

一方、動画書き出しでは映像MP4と音声WAVを別々に扱う必要がある。従来のfilter_complexへ音声を同時投入すると、入力index、trim、filter graph、再エンコードのどこかで音声streamが落ちる可能性がある。

v5.5では、ゲーム音だけの場合は以下に分離する。

```text
raw video
   ↓
映像エフェクト + NVENC
   ↓
完成映像
   ↓
WAV + AAC mux（映像copy）
   ↓
最終MP4
```

この方式ではゲーム音を追加するために映像を再エンコードしない。

## 9. 音声同期

- 音声録音開始時刻 `audio.t0`
- 映像録画開始時刻 `rec.started_perf`
- `audio_offset = rec.started_perf - audio.t0`
- WAVをoffset分trim
- クリップ長に合わせてpad/trim
- AAC 192kbps / 48kHz / stereo

## 10. エフェクト設計

### GPU優先

入力動画を可能な場合CUDAフレームへ置き、GPU scaleを優先する。

色補正、curves、vignette、noise等のCUDA版が安定して存在しない処理はCPU filterとして実行する。その後NVENCで最終エンコードする。

### カーブ

`CurveEditor` はCanvasベース。

- ヒストグラム
- グリッド
- 45度基準線
- 制御点
- ドラッグ
- 文字列保存

ポイント形式:

```text
0/0 0.25/0.20 0.50/0.50 0.75/0.80 1/1
```

## 11. 初心者向け設計

詳細編集を隠すのではなく、詳細編集の上に「かんたん作成」を置く。

```text
★ かんたん作成
① リプレイを開く
② 対象プレイヤーを選ぶ
③ 自動作成
```

テンプレートには既存のHERO/CLEAN/HYPE/LoLnam系を維持し、初期状態でも実用的な結果が出るようにする。

## 12. 検出シーンUI設計

検出カードは以下の順序で固定する。

1. 検出リスト
2. チェック切替 / 選択シーンへ移動
3. 全選択 / 全解除
4. 選択シーン作成
5. チェック済み作成
6. 全シーン作成

これにより、画面下端にボタンが隠れても主要操作が失われない。

## 13. 出力フォルダ

`self.out_root` を唯一の出力先として扱う。

- UIから変更
- 右パネルにも表示
- 出力カードにも表示
- 「開く」でExplorerを開く

## 14. エラー処理

- Replay APIエラー: クリップ単位で停止／diagnostics記録
- 音声エラー: 音声付き設定なら失敗扱い
- FFmpegエラー: stderr末尾をログへ記録
- NVENC失敗: CPU fallback可能な箇所で切替
- アプリ全体のクラッシュを防ぐためバックグラウンド処理例外をUIへ通知

## 16. 既知の制約

- この開発環境ではWindows上の実LoL Replay、WGC、NVENC、Process Loopbackを完全再現できない。
- そのため実機での最終確認項目は、NVIDIA GPU、LoL音声、144Hz表示、実Replay APIで確認する必要がある。
- CUDA対応フィルタはFFmpegビルドによって異なるため、非対応フィルタはCPUへ戻る。
