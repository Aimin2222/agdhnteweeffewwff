# 実装後の受入確認手順

今回用意した台帳は、3UI共通42件、候補3維持必須20件、R1/R2固有12件、3UI×70機能210件の計284件です。**すべてNOT_RUN**。過去の研究デモのPASSやPR51のオフライン試験を今回の結果へ転記しません。

1. Codexからビルド/コミット、3UIの画面ID、スクリーンショット、DPIとクライアント寸法、実操作ログ、未接続/未対応一覧を受け取ります。現在のBAT版の指摘もこの証拠が来てから差分判定します。
2. SOURCE_INDEX.jsonで正本を選択し、候補3・R1・R2それぞれ同じサイズ/テーマ/状態で比較します。C3-P/Sを候補3の基準にしません。
3. 候補3はG0〜G5を先に検査します。メインのパネル・タブ・下段・密度が崩れていれば、動作があっても忠実再現としてFAIL。原画を好きという評価を「簡略化してよい」と読み替えません。
4. R1は左シーン/右設定/下トラック、R2は左レール/右設定/下ショット列を検査。見た目だけ似ていて、別の機能へ繋がる場合は機能受入FAILです。
5. 詳細・カメラ・カーブ・色・素材・出力を巡回し、ProjectStore、固定ミラー、フォーカス/チェック、数値/キー/ドラフトの保持を確認します。似た機能を統合した場合はcapability/対象/単位/副作用/保存の同一性を確認します。
6. 70項目それぞれ入口から辿り、実能力を確認します。未実装項目は説明が正しいことだけを別に評価し、機能成功にしません。

数値比較：パネル辺、ボタン位置、映像面、文字/行高、見える人数/シーン行/カード数、スクロール範囲を記録。画像重畳や差分の補助には前回資料 `c3_acceptance_20261027/tools/compare_screens.py` を使えます。サイズ不一致を黙ってリサイズせず、変換した場合は変換値を記録します。UI境界やボタンを差分マスクへ入れません。

R1/R2のステージ寸法は元のpng.metrics.jsonから取得し、全20枚をSOURCE_INDEX.jsonへ保存しています。過去のbodyOverflow=falseは今回の再試験ではありません。R2の1080版下部270pxはショット列37px＋その下の編集部約233pxのスタックであり、270pxの編集部をさらに下へ足す設計にしません。狭幅版は元PNGの配置を優先します。

候補3の原画ライトを基準にし、ダーク/1366適応は派生状態として別に評価。R1/R2にはdark main/1366 mainの原画像がありますが、他の狭幅設定画面は未提供の派生状態です。別画像を正本に見せません。

主観の好みはEVIDENCE_TEMPLATE.jsonのsubjective_preferenceへ、数値/操作の合否と分けます。PASSは当該検査の実証に限定し、証拠不足はREVIEW、未実施はNOT_RUN、構造欠落/誤接続/偽成功/承認変更はFAIL。重大FAILを平均点で相殺しません。

実LoL/BLUE/RED/TargetLock、GPU、音声、MP4、ネイティブDPI、フォーカス/IME/ポインタは今回未実施です。ユーザーPCのネットワーク・セキュリティ・全体音量の設定変更なしで、Codex側が検証環境を準備します。配布停止デモは起動・復元しません。
