# 不明機能を調査するルール

Codexが不明な部品を見つけた場合はRESEARCH_REQUEST_TEMPLATE.jsonの形で、UI/画面ID/原画像SHA/部品の位置と文言/実装コミット/期待する役割/現在の動作を記録します。名前だけで調査しません。まだ質問が来ていない項目は「既知の曖昧点」とし、実際の依頼・回答済み案件を捏造しません。

1. 元画像の周囲・タブ・説明を確認し、部品の役割をまず言語化します。画像から分かるのは見せ方であり、エンジンの実装有無ではありません。
2. 既存70項目のsource/handlerを固定コミットで読み、最新実装を必要に応じて読み取り専用で照合します。過去の「実装確認」を今回の実接続成功へ繰り上げません。
3. 入力対象、単位/範囲、時刻系、対象シーン、適用範囲、保存先、出力、副作用、実行タイミングを比較します。すべて一致する場合だけEXACT。部分対応はPARTIAL、名前が似るだけならSIMILAR_NOT_EQUIVALENTです。
4. 対応が無い場合はNEW、根拠不足ならUNRESOLVED。近い機能へ無理に吸収せず、不足能力と必要なデータ・テストを明記します。完全新規の実装は今回実施しません。
5. 配置は処理の段階と対象に合わせ、同じUIの既存タブの詳細へ付随。新しい主画面・大きいタブへの変更は提案としてユーザーへ示します。
6. 回答は「本来の役割/既存の近い機能/相違点/配置先/必要な新規部分/根拠/未検証事項」のセットで保存し、Codexが接続した後に別の受入検査を行います。

資料だけで意味が確定できない場合は、その不足を短く説明します。例：候補3の「画像選択」は、図鑑か参考画像抽出かを確定できないため、原画の位置は維持し、対象形式と適用効果を確認するまで別処理へ結線しません。

調査開始済みの曖昧点14件をUNKNOWN_FUNCTION_REGISTER.jsonに記録しました。設計上の方針は用意しましたが、最新実装の検証やすべての意味の確定はOPENです。現在BAT版の差分も、実物のスクリーンショットとビルドIDが届くまでNOT_RUNです。
